## Defects observed in this run

### 1. Fabricated-IDs are mostly natural-language side labels

`fabricated_evidence_ids`: 24 (hunk-only), 1 (selected), 8 (full-bundle).
Inspection shows nearly all quoted IDs are the strings `"ours"` or `"theirs"`
(or `"ours vs source:theirs"`) — natural-language references to the conflict
sides that the prompt's SYSTEM_PROMPT tells the model to use. The aggregator's
"fabrication" check (`_aggregate.ts:108`) treats any quoted tag not present in
the corpus's `triple_key` set as fabricated, so legitimate side-name
references get counted. **These are not real fabrications of evidence SHA-IDs.**
A future patch could distinguish `[source:ours]` / `[source:theirs]` from
arbitrary quoted text, but the verdict's accounting of wrong/correct/halt is
not affected.

### 2. `aggregate.json` `seed_subsample` / `repeats` are 0

The aggregator reads `process.env.H0_SUBSAMPLE` / `H0_REPEATS` to populate
`seed_subsample` / `repeats` in `aggregate.json` (`_aggregate.ts:344-345`).
These env vars were exported only in the runner's shell, not in the
aggregator's shell — so they read as `0`. The actual subsample (30) and
repeats (3) are recoverable from `triples_total: 30` in `arms.*` and the
per-arm records (3 runs each × 30 triples = 90 records). **Not a verdict
defect; cosmetic metadata.**

### 3. full-bundle wrong-count delta vs hunk-only is 4 (gap 3.8pp)

The plan text specified a 5-percentage-point gap threshold between the best
arm's `wrong/(wrong+correct+halt)` and hunk-only's for "evidence utility
confirmed" (`h0-rerun-after-redesign-plan.md:93`). The actual gap is
-0.037 (best = full-bundle at 0.318; hunk-only at 0.356). The plan's 5pp
threshold is **not** met. The aggregator's own verdict logic
(`_aggregate.ts:319-324`) does not implement the 5pp rule — it uses a
`wrong < wrong` count comparison instead, which produces a `positive`
verdict here. **This discrepancy between plan-text and aggregator logic was
surfaced to the user; the user elected to trust the aggregator's verdict.**

### 4. `seed_subsample=0` would mislead future re-aggregation

A future run of `_aggregate.ts` without `H0_SUBSAMPLE` exported will
overwrite `aggregate.json` with `seed_subsample: 0`. The next read of this
file should be done with `H0_SUBSAMPLE=30 H0_REPEATS=3` exported, so the
metadata reflects the actual subsample.

### 5. One `schema_valid=false` record in full-bundle (triple 18/30 run 1)

The 90s fetch timeout fired on that call — `wall=90027ms`, `tok=0+0`. The
record's `decision: "halt"` (defaulted by the parser when content is empty)
and `schema_valid: false` cause the aggregator to count it as
`schema_invalid` (line 96-99), keeping the `wrong/(wrong+correct+halt)`
denominator finite. The kill branch stays reachable. A future patch could
distinguish "fetch timeout" from "LLM genuinely returned invalid JSON".

## Residual

### A. trivial_ceiling uses different denominator than model arms

`_aggregate.ts:256-269` derives `trivial_ceiling` from `baselines.json`,
which contains 862 baseline records (one per triple in the full corpus,
not just the 30-triple subsample). The model arms aggregate over the 30
subsampled triples (90 records each = 30 × 3 repeats). This means
`trivial_ceiling.compose.wrong=1260` is computed from 862 triples, not 30,
which is what makes `composeWrongFraction = 1260/862 = 1.462` look
"worse than 100%". The kill condition therefore says `bestModelWrongFraction
= 0.318 >= composeWrongFraction - 0.5 = 0.962 → false`, which is the
"model wins" half of the kill condition. The verdict is not affected; this
is a documentation gap in the aggregator that should be patched (subsample
the baseline to the same 30 triples) before any further H0 runs.

### B. Per-arm aggregate double-counts from baselines.json

The aggregator's `main()` reads every `runs/*.jsonl` (including
`*-2026-08-27T10-27-45-544Z.jsonl` files from the invalidated first run) and
**also** appends `baselines.json` to the file list. For baseline arms, the
per-arm file (90 records from this run) is processed first and overwritten
by `baselines.json` (2694 records from the full corpus). The "last wins"
behavior produces correct verdict numbers for model arms (which are only in
the new files) but produces inflated baseline counts in `aggregate.json`
(862 triples instead of 30 for the trivial_ceiling; see §A). For verdict
purposes this is harmless — model-arm numbers are unaffected — but the
baseline numbers in the published `aggregate.json` are not directly
comparable to model-arm numbers. Future cleanup: move
`*2026-08-27T10-27-45-544Z.jsonl` files out of `runs/` (they are byte-stable
artifacts under `RETRACTED/` per `RETRACTION.json`) or have the aggregator
filter to the current-run timestamp.

## What this verdict does NOT do

- It does not claim the model is "smart". Wrong-fraction is 0.32-0.46 across
  arms, so even the best arm is wrong on roughly one in three merges.
- It does not prove full-bundle is universally better than hunk-only. The
  delta is 4 triples (out of 90 records), p ≈ 0.13 by sign test, not
  statistically significant at conventional thresholds. The verdict's
  `positive` classification comes from the aggregator's design intent, not
  from a significance test.
- It does not address the fabricated-IDs defect: the regex parser treats
  natural-language side labels as fabricated. A future patch is needed.
- It does not retroactively validate the 2026-08-27 first run. The
  invalidated artifacts stay in `RETRACTED/` and are byte-stable per
  `RETRACTION.json`.
