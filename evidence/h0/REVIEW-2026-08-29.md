## Defects observed in this run

### 1. Invalid source-ID citations — DISQUALIFYING

`fabricated_evidence_ids`: 24 records (hunk-only), 1 (selected), 8
(full-bundle) at the aggregator level: **33 invalid records**, containing
**41 invalid tag occurrences** across 7 distinct values. The runner-level
`fabricated_ids` flag is true on 34 records because any quoted tag sets it;
one of those records cited its own exposed triple key and was correctly
downgraded by the aggregator.

The aggregator's `knownTripleKeys` set is **not empty**: it contains 862
corpus triple keys loaded from the jq and cli materialized corpora. The prompt
permits only source IDs actually exposed to the model. Tags such as `"ours"`,
`"theirs"`, `"ours vs source:theirs"`, `"line_number_change"`,
`"line_numbers"`, and `"token_reordering_conflict"` were not exposed source
IDs and are not corpus triple keys. They are validity failures, not legitimate
side-name references and not regex false positives.

`h0-rerun-after-redesign-plan.md:117` declares the entire run **INVALID** if
any arm has `fabricated_evidence_ids > 0`; this run has 33 such records.

### 2. `aggregate.json` `seed_subsample` / `repeats` are 0

The aggregator reads `process.env.H0_SUBSAMPLE` / `H0_REPEATS` to populate
`seed_subsample` / `repeats` in `aggregate.json` (`_aggregate.ts:344-345`).
These env vars were exported only in the runner's shell, not in the
aggregator's shell — so they read as `0`. The actual subsample (30) and
repeats (3) are recoverable from `triples_total: 30` in `arms.*` and the
per-arm records (3 runs each × 30 triples = 90 records). **Not a verdict

However, that user-side choice does NOT clear the plan-rule verdict:** the run remains INVALID per `h0-rerun-after-redesign-plan.md:117` (33 records with `fabricated_evidence_ids > 0`). The aggregator's `positive` is preserved as non-binding characterization of the count-based comparison, not as a binding H0 outcome.

## Residual

### A. trivial_ceiling uses different denominator than model arms

`_aggregate.ts:256-269` derives `trivial_ceiling` from `baselines.json`,
which contains 862 baseline records (one per triple in the full corpus,
not just the 30-triple subsample). The model arms aggregate over the 30
subsampled triples (90 records each = 30 × 3 repeats). This means
`trivial_ceiling.compose.wrong=1260` is computed from 862 triples, not 30,
which is what makes `composeWrongFraction = 1260/862 ≈ 1.462` look
"worse than 100%". The code's kill-condition denominator is `hunkOnly.triples_total = 30`, so `bestModelWrongFraction = min(28, 41, 32) / 30 ≈ 0.933` (wrong-records per unique triple in the model arm), and `composeWrongFraction = 1260/862 ≈ 1.462` (wrong-records per unique triple in the trivial baseline). Both populations are *wrong-records per unique triple* (same unit), but **same-unit does not mean same-coverage**: 30 unique triples from the model arms, 862 unique triples from the trivial baselines, on a corpus the model arms didn't see. The boolean `kill_condition.met = false` is technically reachable (D5's structural form is fixed), but the comparison mixes 30-triple coverage with 862-triple coverage — the `≥` test is not a meaningful gate. **The verdict IS affected** by this denominator mismatch: `honest_signal = true` is a vacuous boolean (bestModelWrong=28 < composeWrong=1260 is not a meaningful comparison because the 28 comes from a 30-triple subsample and the 1260 comes from a 862-triple full corpus). This is a documentation gap in the aggregator that should be patched (subsample the baseline to the same 30 triples) before any further H0 runs.

### B. Per-arm aggregate double-counts from baselines.json

The aggregator's `main()` reads every `runs/*.jsonl` (including
`*-2026-08-27T10-27-45-544Z.jsonl` files from the invalidated first run) and
**also** appends `baselines.json` to the file list. For baseline arms, the
per-arm file (90 records from this run) is processed first and overwritten
by `baselines.json` (2694 records from the full corpus). The "last wins"
behavior produces correct verdict numbers for model arms (which are only in
the new files) but produces inflated baseline counts in `aggregate.json`
comparable to model-arm numbers. **For the INVALID plan-rule verdict, this is meaningless** — the run is invalid regardless of whether the baseline denominators line up. Future cleanup: move
`*2026-08-27T10-27-45-544Z.jsonl` files out of `runs/` (they are byte-stable
artifacts under `RETRACTED/` per `RETRACTION.json`) or have the aggregator
filter to the current-run timestamp. The "harmless" framing here applies only to whether the model-arm correct/wrong/halt numbers themselves are reproducible — not to whether the run clears the plan-rule.
### C. Run-level gate failures: PRNG, sample diversity, dependency feed, citation check

The H0/WP8 acceptance gate did NOT pass for four interlocking reasons that are captured here as one consolidated "Residual C":

1. **PRNG broken (S4 / `subsample()` stride-based).** `_h0_runner.ts:249-250` reads `let t = Math.imul(a ^ (a >>> 15));` followed by `t = (t + Math.imul(t ^ (t >>> 7))) | 0;`, where both `Math.imul` calls pass only one argument; `Math.imul(x)` coerces the missing second arg to `0`, so both calls return `0`, and the Fisher-Yates collapses to a one-position rotation. The canonical Mulberry32 is `t = Math.imul(t ^ t >>> 15, t | 1); t ^= t + Math.imul(t ^ t >>> 7, t | 61); return ((t ^ t >>> 14) >>> 0) / 4294967296;` — the second-argument masks (`t | 1`, `t | 61`) are part of the algorithm's bit-diffusion design, not interchangeable with a literal `1` or "any constant." Effect: every call to `mulberry32()` returns `0`, regardless of seed value. Tested with seeds 1, 42, 100, 1000, 99999, 12345, 999999; all give the same 30-jq sample (0 cli triples). The plan's "≥2 languages" requirement is therefore violated *at the sample level* by PRNG degeneracy, not just at the corpus level.

2. **Sample diversity (≥2 languages / ≥3 repos).** Even with a fixed PRNG, the corpus has only 2 repos (`stedolan/jq`, `cli/cli`), failing the ≥3-repos requirement outright. The full corpus contains 377 jq triples and 521 cli triples, but with the broken PRNG only jq triples are drawn into the sample.

3. **Dependency feed not used (S5 / `DEPENDENCY_LIST` hardcoded).** The redesigned runner still hardcodes `<<DEPENDENCY_LIST>>\n(none — single-file conflict)<<END_DEPENDENCY>>` in the `selected` arm prompt (line 105) and `<<DEPENDENCY_LIST>>\n(none)<<END_DEPENDENCY>>` in the `full-bundle` arm prompt (lines 113 and 130), ignoring the `dependency_graph` field that PR-C populated in `triples-{jq,cli}-diff3.jsonl`. The `selected` arm therefore does not present real dependency info to the model — it sees the conflict hunk plus a hardcoded `(none)` placeholder. The arm's output measures prompt padding rather than evidence selection. (This is one reason the verdict's "selected" arm (correct=46, wrong=41, halt=3) is not informative about selection utility.)

4. **Citation validity — DISQUALIFYING per plan-rule.** The aggregator flags
33 of 270 model-arm records (24 hunk-only + 1 selected + 8 full-bundle), with
41 invalid-tag occurrences across 7 distinct values. The prompt permits only
exposed source IDs; `"ours"`, `"theirs"`, `"ours vs source:theirs"`, and the
other flagged strings were not exposed source IDs and are not among the 862
known corpus triple keys. These are validity failures, not legitimate
references. `h0-rerun-after-redesign-plan.md:117` declares the run invalid if
*any* arm has `fabricated_evidence_ids > 0`; this single rule is sufficient to
make the 2026-08-29 run **INVALID**.

The four failures above (PRNG broken, sample diversity, dependency feed unused, citation check disqualifying) collectively drive the **RUN INVALID** verdict per the plan-rule (single-flag rule on `fabricated_evidence_ids > 0` is sufficient on its own). The same population of unclosed defects is referenced as S3/S4/S5 in `phase-plans/INDEX.md` and §3.4 of `canonical-final-planning-document.md`. The run is invalid; WP8 remains gated on a future rerun with (a) PRNG fix, (b) ≥3 repos / ≥2 languages corpus, (c) S5 dependency-feed fix, (d) citation-validity fix or any-flag rule amendment, and (e) a working human/scripted adjudicator harness.

## What this verdict does NOT do

- It does not claim the model is "smart". Wrong-fraction is 0.32-0.46 across
  arms, so even the best arm is wrong on roughly one in three merges.
- It does not prove full-bundle is universally better than hunk-only. The
  delta is 4 triples (out of 90 records), p ≈ 0.13 by sign test, not
  statistically significant at conventional thresholds. The verdict's
  `positive` classification comes from the aggregator's design intent, not
  from a significance test.
- It does not provide valid source-citation behavior. The prompt permits only
  exposed source IDs, while 33 records contain 41 invalid tag occurrences.
  The aggregator correctly detects that the 7 distinct invalid strings are
  absent from the 862-element known triple-key set. This is a runner/prompt
  validity defect, not a legitimate-reference false positive. A future run
  must either expose valid evidence IDs and require exact citations or emit
  no `[source:…]` tags; the plan's any-flag rule otherwise invalidates the run.
- It does not retroactively validate the 2026-08-27 first run. The
  invalidated artifacts stay in `RETRACTED/` and are byte-stable per
  `RETRACTION.json`.
