### WP5 — M2a port to `@mrgr/mechanisms` (parallelizable with the H0 rerun)
- **Partially done (2026-09-02, corrected 2026-09-02 after review).** An earlier pass on this page called WP5 "Done" against the acceptance-gate bullets below, without reconciling that against the fuller Deliverable paragraph it sits next to — the two describe different scopes, and the code only satisfies the narrower one. Corrected here to state plainly what's proven and what's deferred; see `../reference/verification-leads.md` for the underlying finding.
  - **Proven:** `packages/mechanisms/` ships `src/adapter.ts` (`runMechanism`, dispatching `git_text`/`gnu_diff3`/`mergiraf`), `src/registry.ts` (`classifyPath`, `mergeFiles`), and `src/index.ts`. `git_text` matches `git merge-tree --write-tree`'s tree OID on a real two-branch fixture (`tests/equivalence.test.ts`). Five runs of the same fixture produce identical merged *blob* OIDs (not tree OIDs — the test itself only hashes merged content with `git hash-object --stdin`, no tree is built there; the test name was corrected 2026-09-02 to stop overclaiming this). `rawStatus` and `normalizedStatus` are reported as two distinct, non-conflated fields. Attribute-pattern routing (`classifyPath`) and the `merge=binary` macro are proven as pure-function unit tests. A D79-style mixed text+binary batch proves per-file independence inside `mergeFiles`'s own loop, in both file orderings. `spawnSync` failures (binary not on `PATH`) and a configurable timeout (`MRGR_MECHANISM_TIMEOUT_MS`, default 30s) both fail closed to `normalizedStatus: 130` without throwing. A mergiraf run that exits claiming success but leaves no readable output file is also forced to `130` rather than silently accepted as an empty clean merge (a real data-loss bug caught in review — see the fix note below). 20/20 tests pass; `@mrgr/core` unaffected (299/299 → 305/305 as its own suite has grown since).
  - **Deferred, not done:** no git-merge-driver integration exists — no CLI entrypoint, no `.gitattributes`/`git config merge.<name>.driver` wiring — so nothing here has ever been invoked by real `git merge`. Concretely that means: **"outer Git" status is not captured** (there are 2 status layers — `rawStatus`, `normalizedStatus` — not the 4 named in the Deliverable paragraph below: this port runs exactly one mechanism per call rather than comparing a git-text raw status against a separate Mergiraf raw status, which is a deliberate design difference from the Round 5.1 driver's flow, not an oversight); **per-attribute `merge=mergiraf` registration is untested against real git** (`classifyPath` is proven as a pure function, but no `.gitattributes` file or git config was ever written and exercised); and **`mergeFiles` returns a per-file outcome array, not a git tree**, so "earlier in-core text result is preserved in the returned tree" is unproven — what's proven is the weaker property that files are independent within this package's own batch loop. Building the missing CLI driver + real git integration is real, separately-scoped work, not a same-day review fix — it isn't started.
  - **CI gap, caught and fixed 2026-09-02:** `mergiraf` is an external Rust binary (`~/.cargo/bin/mergiraf`), not a workspace dependency, and `.github/workflows/ci.yml` doesn't install it. The two `mergiraf`-specific tests in `tests/adapter.test.ts` are guarded with `describe.skipIf(!mergirafAvailable())` (checked, both by running with `mergiraf` present and by pointing `MERGIRAF_BIN` at a nonexistent path to confirm the skip fires) — they'll skip in CI rather than fail there, and only actually exercise the mergiraf mechanism on a machine that has the binary. Installing `mergiraf` in CI (so this mechanism gets real coverage there too) is left as follow-on work, not done here.
